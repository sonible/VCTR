# sonible C++ Documentation Check

Audits the documentation of VCTR's C++ sources (`.h`, `.tpp`, `.cpp`) against the sonible documentation style as
used throughout `include/vctr/`. The docs are rendered with Doxygen (`Doxyfile` in the repo root), so every rule here
also keeps the generated reference clean. When this file and the existing code in `include/vctr/` disagree, the
prevailing style of the existing code wins.

## Workflow

1. **Scope**: files the user named; otherwise all C++ files under `include/`, excluding `ext/`, build directories and
   generated code. Tests (`test/`), `demo/` and `benchmark/` only when named.
2. **Collect** every class/struct, class template, function template, free function, public member function and
   `constexpr inline` expression builder (`ExpressionChainBuilder` instances).
3. **Check** against the rules below.
4. **Report** as `path:line  RULE  message`, grouped by file, with a final count. Rule IDs: `PRESENCE`, `SUMMARY`,
   `TPARAM`, `PARAM`, `RETURN`, `INGROUP`, `MATH`, `FORMAT`, `INLINE`.
5. **Fix** the violations directly, without waiting for approval. Never invent behavior: write descriptions from what
   the code actually does; if intent is unclear, keep the wording conservative and list it in the final summary.
6. **Verify**: re-run the check, then `scripts/verify.sh -s docs` (needs `doxygen`) and compare the warning count
   with the count before your changes; it must not grow. Change comments only, never code.

## Comment form

- Declaration docs use `/** ... */` placed directly above the declaration (above the `template <...>` line).
- The summary starts on the `/**` line. Following lines are indented to the text column of the summary (4 spaces past
  the `/**`), without a leading ` * `. The closing ` */` sits on its own line, one space past the `/**` column.
- Short inline docs for (enum) constants might use `///` on the same line. 
  Example: `static constexpr auto x = 2; ///< constant scaling factor`
- Not `/*! */`, or `//` for declaration docs.
- Tags use `@` (`@tparam`, `@param`, `@return`, `@ingroup`, `@code`/`@endcode`, `@see`, `@note`), never `\`.
- Wrap prose at about 120 columns, like the surrounding code.
- One-line docs are fine for simple entities: `/** Collection of static methods for generating evenly spaced numbers. */`

## Presence (`PRESENCE`)

Document:

- Every class/struct and class template in the public `vctr` namespace.
- Every public expression builder (`constexpr inline ExpressionChainBuilder<...> name;`) and every free function that
  creates an expression (`makeExpressionChainBuilderWithRuntimeArgs`, binary operators/functions).
- Non-trivial public member functions of the containers and of `VctrBase`.
- Concepts in `vctr::is`, `vctr::has`, `vctr::are` whose meaning is not obvious from the name.

Do not flag:

- Members of `vctr::expressions` classes that are generated by the `VCTR_COMMON_*_EXPRESSION_MEMBERS` macros, or the
  `operator[]`, `getAVX`/`getSSE`/`getNeon`, `evalNextVectorOpInExpressionChain` and `reduce*` evaluation hooks. The
  user-facing documentation lives on the builder in the `vctr` namespace.
- Entities in `detail` namespaces with a clear name.
- Forwarded `std` members (`size()`, `push_back()`, ...) whose behavior matches the standard library.
- Type aliases and `static constexpr` mirrors of template parameters when the class docs describe the parameter.
- Overrides/overloads whose sibling declaration is documented.

Keep the LGPL license header as is; it is handled by the `fix-file-headers` skill.

## Block structure (`SUMMARY`)

Separated by blank lines, in this order:

1. **Summary**: one sentence ending with a period, describing what it is or computes, not its name.
   Good: `Computes the product of the source values.` Bad: `Product expression.`
2. **Description paragraphs**: behavior, edge cases, numerical caveats ("can quickly overflow integer types"),
   constraints and supported element types, allocation behavior, differences between the accelerated and the
   fallback path, and usage examples in `@code` / `@endcode`.
3. **Formula** (when behavior is mathematical, see `MATH`).
4. **Tags**: `@tparam`, then `@param`, then `@return`, then `@see` / `@note`, and `@ingroup` last.

## Template parameters (`TPARAM`)

- One `@tparam name Description.` per template parameter of a documented template, in declaration order, none
  missing, none extra (type, non-type, concept-constrained, and packs all count).
- Exceptions: the `extent` and `SrcType`/`SrcAType`/`SrcBType` parameters of classes in `vctr::expressions` (they are
  part of the expression template machinery and documented in `include/vctr/Expressions/Readme.md`).
- Descriptions start right after the name; no colon after the name (`@tparam minDb The lower threshold ...`, not
  `@tparam minDb: The lower ...`). Aligning descriptions of consecutive tags into one column is fine.
- State constraints enforced by the `requires` clause / concept, e.g. `Must be a real floating point type.`

## Function tags (`PARAM`, `RETURN`)

- `@param name Description.` for every parameter of a documented non-trivial function, in signature order, names
  exactly as in the signature.
- `@return Description.` when the return value is not obvious from the summary (`Returns a Vector with ...` in the
  summary already covers it).
- Mention preconditions (`must be > 0`), size requirements, aliasing rules and whether the function allocates.
- Small self-explanatory functions may have a summary only; don't add tags that merely repeat the name.

## Doxygen groups (`INGROUP`)

- Every public expression builder and expression-creating free function ends with `@ingroup Expressions`.
- The core container types (`Vector`, `Array`, `Span`, `VctrBase`) use `@ingroup Core`.
- Don't add `@ingroup` to `detail` entities or to members of a class that already has one.

## Math and formulas (`MATH`)

When behavior is defined by an equation, state it in the description in plain text using the same names as the code,
either inline (`The calculation is max (constant * log10 (src), minDb).`) or as an indented block introduced by a
sentence ending in `:`:

```cpp
/** Computes the sum of the squared source values.

    For a source of size n, the result is:

        result = src[0]^2 + src[1]^2 + ... + src[n - 1]^2

    @ingroup Expressions
 */
```

Flag when a numeric expression has no formula or plain-language mapping, when the formula names don't match the code,
or when relevant facts are missing: units (dB variants), valid input ranges, behavior at the boundaries (zero, negative
input to `log`, empty sources), and precision differences of approximations (`fastLog2`, `fastExp2`).

## Inline comments (`INLINE`)

- Inside bodies, explain **why** or non-obvious index math; full sentences on the line(s) directly above the code.
- Don't narrate the obvious (`// loop over elements`).
- Flag uncommented non-obvious things: SIMD tail handling, alignment assumptions, `std::is_constant_evaluated()`
  branches, workarounds for a specific compiler, and `// clang-format off` regions without a reason.

```cpp
// The SIMD loop only covers full registers. The remaining size % registerSize elements are
// processed with the scalar operator[] fallback.
```

## Formatting (`FORMAT`)

- Summary and tag descriptions end with a period.
- Blank line between summary, description, formula, and tag groups.
- No trailing whitespace (also not on otherwise blank lines inside a comment).
- Use `@note` in lowercase; `@Note:` is not a Doxygen command.
- Docs match code: no stale names, removed parameters, outdated formulas, or references to renamed functions.
- No duplicated prose between class and member docs.

## Examples

```cpp
/** Computes the product of the source values.

    Note that the product of a long sequence can quickly overflow integer types or under-/overflow
    floating point types. With SIMD acceleration, the multiplication order differs from a
    sequential evaluation, so floating point results might differ slightly.

    @ingroup Expressions
 */
constexpr inline ExpressionChainBuilder<expressions::Product> product;
```

```cpp
/** Returns a Vector with evenly spaced numbers between start and stop.

    If start and stop are identical, the container will be filled with that value. Ranges can have a negative
    increment, i.e. start > stop is explicitly allowed.

    @tparam ElementType Element type contained in the vector.

    @param start      First value of the interval; always included.
    @param stop       Last value of the interval; only included if includeEnd is true.
    @param num        Number of elements (length of the vector), must be > 0.
    @param includeEnd If this is true, both start and stop are included; otherwise only start is included.
 */
template <is::realNumber ElementType>
static Vector<ElementType> makeVector (ElementType start, ElementType stop, size_t num, bool includeEnd = true);
```

### Violations

```cpp
// WRONG: `//` style, summary repeats the name, no @ingroup.
// clamp expression
template <auto lowerBound, auto upperBound>
constexpr inline ExpressionChainBuilder<expressions::ClampByConstant, Constant<lowerBound>, Constant<upperBound>> clampByConstant;
```

```cpp
// WRONG: colon after the tparam name, a tag for a parameter that doesn't exist, `@Note:` instead of `@note`.
/** Converts the source magnitude into a decibel representation.

    @Note: Uses log10.

    @tparam DecibelConstant: Either vctr::dBFS, vctr::dBVoltage or vctr::dBPower.
    @tparam minDb: The lower threshold.
    @param src The source.
 */
```

```cpp
// CORRECT
/** Converts the source magnitude into a decibel representation.

    The calculation is max (constant * log10 (src), minDb), with constant being either 20 for dBFS or dBVoltage
    or 10 for dBPower.

    @tparam DecibelConstant Either vctr::dBFS, vctr::dBVoltage or vctr::dBPower.
    @tparam minDb           The lower threshold for the resulting dB value and thus the value for a magnitude of 0.

    @ingroup Expressions
 */
```

## Fix strategy

1. Apply fixes immediately after reporting; no approval step. Finish with a summary of what changed and any
   descriptions that need human review.
2. **Missing**: write the block from the declaration and body; derive formulas from `operator[]` (the scalar
   reference path), stay conservative when intent is unclear.
3. **Incomplete**: add missing `@tparam`/`@param`/`@return`/`@ingroup` and formula statements.
4. **Malformed**: convert `///`, `/*!`, `\param` and ` * `-prefixed blocks to the form above; reorder tags; fix
   wrapping.
5. **Preserve intent**: keep existing wording; change only what is non-compliant.
6. Never change code or include order. Use the project's call style (`f (x)`, `size()`) in any example code you write
   into comments.
